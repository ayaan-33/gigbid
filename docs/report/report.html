GigBid: R&D design review

AI-4016 Assignment II · individual · open-weight models only (Groq free tier and local Ollama; $0 spent). Every number cites a file in evals/results/. The tables in the appendix are generated from those files by scripts/make_readme_tables.py, and CI fails if a README number doesn't trace to one.

1. Problem and constraints

Workflow. A freelancer's day looks like this: 1. scan feeds; 2. judge fit and risk; 3. price the bid; 4. write a proposal that proves fit, and spend Connects; 5. answer replies, book interviews and win the work.

The expensive failures are: - Connects wasted on unwinnable jobs; - generic proposals that clients ignore; - scams (unpaid "trials", off-platform payment); - proposals that claim experience the freelancer doesn't have.

What must never be automated: sending a proposal or message, spending Connects, agreeing to off-platform contact or payment, claiming unproven experience, or scraping any marketplace. In GigBid these are structural, not prompt-level: - One write path: the graph's only write path is approval.py::submit, reachable only after an interrupt() that a human resumes. - No auto-send: the autonomy setting can only auto-skip. - Guarded writes: marketplace writes need approved_by plus an idempotency key, and are audited in a hash chain. - Drafts only on Upwork: live Upwork writes are drafts the user confirms on Upwork.

Declared budgets (agent/config.yaml):

Budget Job analysed Proposal
p95 latency 25 s 60 s
Cost (list price; actual spend $0 on the free tier) $0.002 $0.006

Per thread there's a 40-step and 30k-token budget; going over moves the thread to needs_attention.

Constraints: - free, open-weight models only; - GigSim wasn't provided, so it was built here and frozen by checksum in CI; - the free-tier limits (about 8k tokens/min and about 200k tokens/day per model) shaped every experiment's size, as stated where it applies.

2. Architecture

Two hand-built LangGraph StateGraphs. Diagrams are rendered from code (make graphs, so docs/images/*.mmd) and shown in docs/ARCHITECTURE.md.

  • Bid graph (one thread per job): 1. ingest (Scout hand-off and fingerprint de-duplication) fans out with Send to the Job Analyst, Risk Assessor and Fit Matcher. 2. A deferred decide node chooses skip, watch or bid. It's deterministic rules on typed hand-offs (ADR 0007). 3. Pricing Strategist (market stats, client spend, the user's floor, Connects expected value and policy-drift detection). 4. Writer, then claim verifier, then Critic. The Critic loops back at most twice. 5. Compliance Guard, which can block. 6. approval_gate: interrupt() with the draft, the evidence behind each claim, the risk report, the price rationale and the dry_run preview.
    • approve → submit;
    • edit → diffed into style memory, then Compliance, then submit (or back to the gate if Compliance changed it);
    • reject → the reason is recorded.
  • Conversation graph (one thread per client conversation): load messages; classify intent with an injection check; find calendar slots (Workspace MCP) for interview requests; draft; run Compliance; interrupt(); send, plus a tentative hold.

Agents exchange Pydantic objects (agent/handoffs.py). State, the execution trace and long-term memory are separate: - State: agent/state.py, with reducers on parallel writes. - Trace: tool_events and run_events, Langfuse, and MCP audit logs, all sharing one trace id. - Memory: the LangGraph store, written only by promotion_rules: - style: a pattern appears in at least 3 of the last 10 edits; - outcome: at least 5 outcomes in a category with a lift of at least 10 points.

MCP surface (Part A). All marketplace access goes through one port (marketplace_port.py) with GigSim and live-Upwork adapters (R1). Only our Marketplace MCP server uses it. The servers: - Portfolio (read-only: 3 tools, 5 resource templates, 4 prompts; published as gigbid-portfolio-mcp). - Marketplace: 10 reads and 3 idempotent writes, with dry_run, Bearer auth, per-user rate limits and a hash-chained audit log. - Workspace: slots, holds and email drafts.

Third-party servers: Upwork's official MCP (OAuth 2.1, tokens Fernet-encrypted per user) and GitHub's official MCP (repo ingestion). Each agent gets an allowlist of tools by name. A circuit breaker gives degraded mode: the UI banner shows, threads queue as queued_degraded, and the worker retries on recovery. The stores are Postgres + pgvector (app data, checkpointer, memory, vectors) and Redis (Arq queue, SSE fan-out).

Why each agent exists. The cheap, frequent nodes are deterministic or use the small model. The large model is used only where language quality pays: the Writer, the Critic and the Client Liaison. The claim verifier is a separate node so that fact-checking is never done by the agent that wrote the claim (docs/ARCHITECTURE.md, "Why each agent exists").

3. R&D question A: does tool granularity change agent behaviour?

Hypothesis. Many narrow tools cost more tokens and cause more wrong-tool choices. Few broad tools are cheap but push errors into the arguments. Rewritten, example-rich descriptions recover accuracy at a moderate token cost.

Setup. 40 tasks with a known correct call, covering every capability. Three tool designs expose the same capabilities: - fine: 26 narrow tools; - coarse: 3 tools with an action enum; - best: our 16 MCP tools with rewritten descriptions.

The model is openai/gpt-oss-20b (Groq free tier) with tool calling. Paced at the free-tier limit; the first call per task is scored. File: tool_granularity_open.json.

Results.

Design Tools Tool selection Arguments Tokens per task
fine 26 0.825 0.825 880
coarse 3 0.950 0.850 505
best (rewritten) 16 0.925 0.925 905

Conclusion. - Fine-grained loses on both counts. It had the most wrong-tool choices, mainly among the four search_* evidence tools, and spent 1.7× the tokens of coarse. - Coarse wins on tool selection and cost. With only three choices, picking one is easy. But argument accuracy drops, because the model has to fill a polymorphic action + id + query schema. - Our rewritten set has the best end-to-end correctness (0.925 for tool + arguments). Two of its three misses were provider 400s on tool-call parsing, not reasoning errors. So the shipped surface stays at the "best" granularity: a tool per intent, with examples in descriptions.

The tokens per task are fixed overhead from the schemas. They matter more for the cheap nodes, which is why each agent only sees its allowlisted subset (3–7 tools, not 16).

4. R&D question B: retrieval, claim verification, and what ships

Hypothesis (stated before running). "Requirement decomposition plus hybrid retrieval raises evidence Recall@5 by at least 15 points over V0 on jobs with four or more requirements."

Setup. - Corpus: 3 synthetic personas with 18–20 case studies, 9–10 repos, 13 reviews and 150 outcome-labelled past proposals each. It was built to defeat naive RAG: three names per project, implied skills, vague READMEs, and proposals dominating the corpus. - Gold evidence: 96 bid jobs per persona, with gold known by construction (DATA_CARD.md). - Recall@5: capped at min(5, |gold|). - Models: embeddings nomic-embed-text-v1.5; reranker chosen by benchmark (ADR 0006: MiniLM-L6 is within 0.02 of bge-reranker-v2-m3 at a tenth of the latency).

Variants (full set, 288 jobs). V0 0.108 → V1 0.187 → V2 0.196 → V3 0.220 → V4 0.214 → V5 0.323 → V8 0.145.

On jobs with four or more requirements, V2 reaches 0.237 against V0's 0.148, a gain of +8.9 points. The hypothesis is not met by decomposition + hybrid alone (+8.9 < +15). It is met only when multi-vector projects are added: V5 reaches 0.358 (+21.0).

V6 (contextual chunk headers) and V7 (HyDE) were evaluated on matched subsets because of free-tier limits: - V6: 0.199 against V3's 0.211 on the same ai_ml jobs; - V7: 0.216 against V3's 0.240 on the same 90 jobs.

Neither helped. HyDE writes in the generic register of past proposals, which are the noise we want to rank down. Context headers made chunks more similar to each other, which blurs the lexical signal that BM25 relies on.

Ablation of the best pipeline (30 jobs per persona, ablation.json):

  • Outcome boosting hurts retrieval: it promotes phrasing (won proposals) over proof.

Claim verification (B3). On a labelled set of 30 drafts × 3 claims (claim_eval_heuristic.json): - the deterministic verifier removed 100% of fabricated claims, caught 90% of tampered numbers, and kept 100% of true claims; - unsupported or wrong claims per draft fell from 2.0 to 0.2.

Where better retrieval didn't raise the reply rate. GigSim's clients grade the opening, specificity, personalisation and price. In the X2 experiment (§7), the strategy moved the reply rate more than retrieval did. Most no-reply cases had good evidence but a generic first sentence, or a bid above the client's hidden ceiling. Retrieval decides what the writer can say; the client reacts to the first two sentences.

Shipped: v5_norerank (ADR 0004).

5. R&D question C: single agent vs prebuilt supervisor vs our graph

local run (qwen3:4b, 6 jobs, the same model for all three systems). Errors are jobs that hit the 600 s per-job cap or a provider error; they count as wrong decisions.

System Bid/skip accuracy Scam recall Unsupported claims / proposal Violations left Tokens / job p95 latency (s) Errors
react 0.5 1 0 0 9145.2 440.6 1
supervisor 0.667 0 1.667 0 9298 600 2
graph 0.5 0 0 0 0 600 4

Reading it. The samples are small (6 jobs), so the differences are indicative only. Three patterns held: 1. The supervisor invents claims. It was the only system that left unsupported claims in its proposals; its sub-agents pass prose, not typed evidence, so the writer cannot cite what it never received. 2. The graph's guarantees are structural. Its scam handling, verification and compliance checks don't depend on the model choosing to call a tool. Its cost is latency: it makes the most calls, so on a 4B local model it hit the time cap on 4 of 6 jobs, including the scam (a timeout, not a wrong call: it never returned a decision). Its zero token count on the local run reflects jobs that timed out before reporting usage. 3. The single ReAct agent is cheapest but least controllable. It skipped every good-fit job, because nothing forces it to gather evidence before deciding.

We kept the graph for its auditability, typed handoffs and approval interrupts; the 600-job decision eval in §3 measures its decision path at scale (F1 0.938 on the hidden set).

6. The change request

  • What changed. GigSim policy v2 adds +4 Connects on jobs with 20 or more proposals, and makes an AI-assistance disclosure mandatory (otherwise the marketplace returns 422).
  • What I edited: 2 lines of agent/config.yaml (policy.version: 2, require_ai_disclosure: true). No prompt or node code changed: the Writer and Compliance read these flags.
  • How long: about 30 minutes, including tests and one real bug the change exposed. Pricing would have added the surcharge on top of the marketplace's already-surcharged figure. It's now fixed by making the marketplace's cost authoritative.
  • What I added: policy-drift detection. The Pricing Strategist compares get_policy against config and warns in the UI. So the next update is noticed on the first job, not on the first rejected submission.
  • Evidence: tests/unit/test_change_request.py covers both before and after the change; the full write-up is in docs/CHANGE_REQUEST.md.
  • What it says about the design: rules belong in config, costs belong to the marketplace, and defence in depth meant nothing non-compliant was sent even before the fix.

7. Signature extension X2: proposal A/B experiments

  • Built:
  • a per-job deterministic arm assignment (A = evidence-first, B = question-led);
  • by-strategy analytics;
  • outcome memory that promotes a winning arm per category;
  • an offline experiment runner with McNemar, two-proportion z, Fisher and a power analysis.
  • Run: 24 fit jobs × 2 arms; the writer was Qwen3 27B (Groq free) for both arms; GigSim's seeded heuristic grader. File: ab_experiment.json.
Arm Reply rate Mean client grade
A: evidence_first 0.417 0.589
B: question_led 0.583 0.644

The difference is −0.167 (95% CI −0.446 to +0.112). - z-test p = 0.248; Fisher p = 0.387. - McNemar (paired) p = 0.125: B won all 4 discordant jobs, A won 0. - Not significant at this size. The power analysis says about 140 jobs per arm would be needed to confirm a 17-point gap with 80% power.

Practical reading: question-led openings look better and never lost here, but we haven't shown it. GigBid keeps A/B assignment on, and outcome memory switches a category to the winner only once the promotion rule has the evidence. The 24 pairs are also the items of the blind human panel (/panel).

9. Safety and platform respect

What GigBid must never do, and how it's enforced: - Send or spend without approval. Writes happen only after interrupt(), and need approved_by, idempotency keys and the audit log. The E2E reject test checks that nothing is sent. - Follow instructions in job posts or messages. These are spotlighted as data, checked by a heuristic and Llama Prompt Guard 2 (100% of planted injections flagged), and attack success went from 20% to 0% after the defences (injection_eval.json). - Leak contact or payment details. Compliance rules run first, and the LLM pass is re-checked by rules. Logs and traces are PII-masked (emails, phone numbers, cards, IBANs, crypto wallets, messaging handles; tested). - Scrape or automate a browser. Live mode uses the official Upwork MCP only, at most every 4 hours (RUNBOOK). - Mix tenants' data. Every query is scoped by user_id, and OAuth tokens are encrypted per user (tested at rest).

What still gets through (honestly): - injected instructions phrased as plausible requirements ("include a link to your portfolio site") pass the detector, though the Writer won't add links because Compliance removes them; - scams from verified-looking clients with no explicit off-platform request; - numbers written in words ("forty percent"), which the number gate misses; - the simulated clients are our model, so reply-rate results don't prove real-world effect.

The dev-tuned threshold generalises: dev F1 was 0.944, hidden F1 is 0.938.

Against the declared budgets: - p95 per job analysed: 12.0 s against the 25 s budget. Met for the decision path (retrieval, rules and pricing). The LLM Job Analyst and Risk Assessor run in parallel and add one small-model call each. - Per proposal: p95 364 s and about 3543 tokens (list price $0.0010). Not met against the 90 s budget on the free tier. Almost all of that time is waiting on the 8k tokens/minute limit (the pacer logs it); on a paid tier the same calls take under 30 s. - Cost: list-price figures are reported per node in the run viewer. Actual spend was $0 throughout (free tier).

What breaks the budget, without excuses. - On Groq's free tier, concurrency is the real risk. With several bid jobs running at once, the token pacer and the provider's retry-after waits pushed single LLM nodes past their 120 s timeout, and two live re-runs went to dead-letter (failure #13). - Fix: a 240 s node timeout, worker concurrency 3, and low reasoning effort except for the Writer. - On a paid tier, or with a self-hosted model, the same graph would sit well inside the budget. On the free tier, the honest p95 for a full proposal is dominated by rate-limit waiting, not computation.

One optimisation that helped. Removing the cross-encoder from retrieval (ADR 0004) cut about 3.3 s from the p95 per job (rag_retrieval.json: V3 at 3.35 s against V5 without reranking) and raised Recall@5. Using the small model for the Risk Assessor and Analyst, plus skipping early on scams and low budgets, means a skipped job costs about 1–3k tokens instead of the 15–19k of a full proposal.
